# Goal Prompt for Codex Spark Design

Используй этот промт как цель для последовательной реализации дизайн-потока AI-коллектора отдельным агентом Codex Spark.

## Цель

Постепенно превратить текущий статический и частично backend-driven интерфейс AI-коллектора в связный compliance-first операторский кабинет: понятный flow кампании, прозрачные состояния, review/QA-контур, controlled launch, автопауза, отчёт и drill-down до evidence.

Главный принцип: реализовывать дизайн и UX маленькими шагами по 1 story point и обновлять дизайн-бэклог после каждой доработки.

## Контекст репозитория

Текущие ключевые файлы:

- `ROADMAP_B2B_SAAS.md` - продуктовый roadmap и UX-gap анализ.
- `DESIGN_BACKLOG_1SP.md` - отдельный рабочий дизайн-бэклог по задачам 1 SP.
- `TECH_BACKLOG_1SP.md` - технический backlog; использовать как соседний контекст, но не как основной список задач дизайн-агента.
- `prototype.html` - главный дизайн-артефакт операторского кабинета.
- `docs/product/prd-open-questions.md` - продуктовые open questions, IA и UX-решения.
- `docs/security/rbac.md` - ограничения ролей и ручных действий.
- `docs/operations/auto-pause.md` - сценарии автопаузы, readiness и safe-resume.

## Рабочий цикл на каждую итерацию

1. Прочитай `ROADMAP_B2B_SAAS.md`, `DESIGN_BACKLOG_1SP.md` и релевантные файлы проекта.
2. Возьми первую задачу со статусом `todo` из `DESIGN_BACKLOG_1SP.md`, если пользователь не указал другую.
3. Перед изменениями поменяй статус задачи на `doing`.
4. Реализуй только эту задачу, не захватывай соседние задачи.
5. Если задача влияет на UX-контракт, обнови связанный документ и/или `prototype.html`.
6. Запусти доступные проверки:
   - ручную проверку flow в `prototype.html`;
   - `npm test` / `npm run typecheck`, если задача задевает JS-логику в прототипе;
   - минимальную проверку diff и состояний, если тесты нерелевантны.
7. Обнови `DESIGN_BACKLOG_1SP.md`:
   - поставь задаче статус `done`, если она завершена;
   - поставь `blocked`, если без внешнего решения продолжать нельзя;
   - поставь `split`, если задача оказалась крупнее 1 SP, и добавь новые мелкие задачи;
   - добавь новые UX/design задачи, если реализация изменила план;
   - уточни `Где менять` у будущих задач, если структура проекта изменилась;
   - добавь запись в `Журнал изменений плана`.
8. В финальном ответе коротко напиши:
   - какую задачу выполнил;
   - какие файлы изменил;
   - какие проверки запустил;
   - какая следующая задача по дизайн-бэклогу.

## Ограничения реализации

- Не реализуй больше одной 1 SP задачи за итерацию без явной просьбы пользователя.
- Не ломай существующие backend-контракты ради визуального удобства.
- Не показывай mock-метрики как production-ready источник правды, если для них нет backend-данных.
- Не скрывай compliance-риск, блокировку, review requirement или источник решения.
- Не превращай чувствительный B2B-интерфейс в декоративный AI-лендинг.
- Если UI обещает действие, которого backend не поддерживает, явно помечай gap или используй безопасный прототипный state.
- Любые destructive / high-risk действия должны быть объяснимы, подтверждаемы и audit-friendly.

## Definition of Done для каждой 1 SP задачи

- Изменения соответствуют описанию задачи.
- Затронутые файлы находятся в разделе `Где менять` или этот раздел обновлен.
- Пользовательский сценарий стал понятнее, безопаснее или воспроизводимее.
- Empty / error / partial / review / blocked states отражены там, где это требуется задачей.
- `DESIGN_BACKLOG_1SP.md` обновлён после реализации.
- Финальный ответ содержит следующую рекомендуемую задачу.

## Как выбирать следующую задачу

Приоритет выбора:

1. Незавершенная задача со статусом `doing`.
2. Первая задача `todo` в блоке `P1`.
3. Первая задача `todo` в следующем добавленном блоке, если дизайн-бэклог расширился.

Если новая задача является зависимостью для текущей, добавь её рядом с текущим блоком и выполни раньше только после явного обновления плана.

## Формат новых задач

Добавляй новые задачи в таком формате:

```md
### D-XXX: Короткое название

Статус: `todo`

Что сделать:

- Конкретное действие 1.
- Конкретное действие 2.

Где менять:

- `path/to/file`

Критерии готовности:

- Проверяемый результат 1.
- Проверяемый результат 2.
```

## Дизайн-принципы для этого агента

- Держи фокус на ролях `collection_manager`, `qa_analyst`, `compliance_officer`, `integration_admin`.
- Проектируй вокруг решений пользователя, а не вокруг технических сущностей.
- Для каждого экрана отвечай на вопросы:
  - что происходит;
  - можно ли безопасно продолжать;
  - почему система приняла это решение;
  - что будет после следующего действия.
- Разделяй:
  - технические события;
  - compliance decision log;
  - review / QA action items;
  - бизнес-результаты звонка.

## Первая рекомендуемая итерация

Если в `DESIGN_BACKLOG_1SP.md` появятся новые задачи со статусом `todo`, начинать с первой такой задачи. Если все текущие задачи уже `done`, следующая итерация должна добавлять новый 1 SP блок только после фиксации следующего UX-gap в `ROADMAP_B2B_SAAS.md` или по прямому запросу пользователя.

# Goal Prompt for Codex Spark 5.3

Используй этот промт как цель для последовательной реализации проекта AI-коллектора.

## Цель

Постепенно превратить текущий статический прототип AI-коллектора в MVP Lab B2B SaaS платформы для compliance-first обзвона: backend API, доменная модель, импорт базы, compliance decision log, sandbox voice provider, журнал звонков, usage ledger и отчеты из реальных событий.

Главный принцип: реализовывать проект маленькими шагами по 1 story point и обновлять технический план после каждой доработки.

## Контекст репозитория

Текущие ключевые файлы:

- `ROADMAP_B2B_SAAS.md` - продуктовый roadmap и исходный backlog.
- `TECH_BACKLOG_1SP.md` - рабочий технический backlog по задачам 1 SP.
- `index.html` - decision dashboard прототипа.
- `prototype.html` - кликабельный кабинет пользователя.

## Рабочий цикл на каждую итерацию

1. Прочитай `ROADMAP_B2B_SAAS.md`, `TECH_BACKLOG_1SP.md` и релевантные файлы проекта.
2. Возьми первую задачу со статусом `todo` из `TECH_BACKLOG_1SP.md`, если пользователь не указал другую.
3. Перед изменениями поменяй статус задачи на `doing`.
4. Реализуй только эту задачу, не захватывай соседние задачи.
5. Запусти доступные проверки: тесты, typecheck, lint или минимальную ручную проверку, если тестового контура еще нет.
6. Обнови `TECH_BACKLOG_1SP.md`:
   - поставь задаче статус `done`, если она завершена;
   - поставь `blocked`, если без внешнего решения продолжать нельзя;
   - поставь `split`, если задача оказалась крупнее 1 SP, и добавь новые мелкие задачи;
   - добавь новые обнаруженные задачи, если реализация изменила план;
   - уточни `Где менять` у будущих задач, если структура проекта изменилась;
   - добавь запись в `Журнал изменений плана`.
7. В финальном ответе коротко напиши:
   - какую задачу выполнил;
   - какие файлы изменил;
   - какие проверки запустил;
   - какая следующая задача по backlog.

## Ограничения реализации

- Не реализуй больше одной 1 SP задачи за итерацию без явной просьбы пользователя.
- Не удаляй и не переписывай существующие прототипы без необходимости.
- Не используй моковые цифры там, где уже есть реальные события или модели.
- Всегда сохраняй tenant isolation для новых данных.
- Любой запуск звонка должен проходить через compliance engine.
- Любое важное действие пользователя должно оставлять audit trail, когда audit log уже создан.
- Секреты integrations и telephony provider нельзя хранить в исходном коде или plain-text моделях.
- Если задача требует выбора архитектуры, сначала создай или обнови decision doc.

## Definition of Done для каждой 1 SP задачи

- Изменения соответствуют описанию задачи.
- Затронутые файлы находятся в разделе `Где менять` или этот раздел обновлен.
- Добавлены или обновлены тесты, если в проекте уже есть тестовый контур.
- Если тестов еще нет, выполнена минимальная проверка запуска или синтаксиса.
- `TECH_BACKLOG_1SP.md` обновлен после реализации.
- Финальный ответ содержит следующую рекомендуемую задачу.

## Как выбирать следующую задачу

Приоритет выбора:

1. Незавершенная задача со статусом `doing`.
2. Первая задача `todo` в блоке `P0`.
3. Первая задача `todo` в блоке `P1`.
4. Первая задача `todo` в блоке `P2`.

Если новая задача является зависимостью для текущей, добавь ее рядом с текущим блоком и выполни раньше.

## Формат новых задач

Добавляй новые задачи в таком формате:

```md
### T-XXX: Короткое название

Статус: `todo`

Что сделать:

- Конкретное действие 1.
- Конкретное действие 2.

Где менять:

- `path/to/file`

Критерии готовности:

- Проверяемый результат 1.
- Проверяемый результат 2.
```

## Первая рекомендуемая итерация

Начать с `T-001: Зафиксировать backend stack`, потому что остальные backend-задачи зависят от выбранных фреймворка, БД, ORM, тестов и локального способа запуска.

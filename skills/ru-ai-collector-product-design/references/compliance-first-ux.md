# Compliance-first UX

## 1. Compliance — не отдельная «галочка»

Проверка должна быть встроена в жизненный цикл действия.

Пользователь должен различать:

- готовность системы выполнять checks;
- решение по конкретному действию;
- причину блокировки;
- risk event после запуска;
- ручной review;
- последствия решения.

## 2. Уровни представления решения

### Уровень 1 — операционный

Для менеджера кампании:

`Звонок заблокирован`

`Причина: требуется дополнительная проверка данных`

`Что делать: открыть запись`

Без внутреннего кода правила.

### Уровень 2 — объяснение

Для supervisor/compliance:

- итог;
- время;
- действие;
- сработавшие проверки;
- человекочитаемые причины;
- policy/ruleset version, если доступна;
- связанные данные.

### Уровень 3 — техническая диагностика

Для администратора/поддержки:

- identifiers;
- raw codes;
- provider/API details;
- correlation ids;
- structured payload excerpts, если это разрешено.

Не смешивай три уровня на одном экране.

## 3. Разрешено / запрещено / review

Если модель поддерживает три исхода, они имеют разный UX:

### Разрешено

Действие может продолжиться.

Не обязательно показывать зеленый banner на каждый обычный звонок. Решение доступно в деталях/audit.

### Запрещено

Действие не должно запускаться.

Покажи:

- что не произошло;
- почему;
- что делать дальше, если действие возможно;
- не давай обходной CTA без политики override.

### Требует проверки

Автоматизация останавливается на человеке.

Покажи:

- почему;
- кому передано;
- что нужно проверить;
- какой SLA/срок только если он реально задан продуктом;
- как решение повлияет на дальнейший процесс.

## 4. Readiness before launch

Перед controlled pilot проверь UX наличия:

- базы;
- обязательных полей;
- доступного provider;
- compliance ruleset;
- event logging;
- review/handoff контура;
- разрешений пользователя;
- stop-condition monitoring.

Не обещай, что система «соответствует требованиям законодательства» только на основании прохождения технических checks.

## 5. Risk banner

Критический banner должен содержать:

1. Severity.
2. Что произошло.
3. Что система сделала автоматически.
4. Что требуется от пользователя.
5. Ссылку на доказательства/детали.

Не делай CTA `Закрыть`, если риск требует действия.

## 6. Auto-pause

Автопауза должна быть объяснима.

Хорошая структура:

`Кампания приостановлена системой`

`Причина: <подтвержденная причина>`

`Новые звонки не запускаются.`

`Проверьте событие и примите решение.`

Фактическое поведение уже начатых звонков бери из backend/PRD.

## 7. Stop conditions

UI может визуализировать только те stop conditions, которые официально определены продуктом.

Для каждого события, если данные доступны, показывай:

- condition;
- threshold/trigger без придумывания;
- first occurred;
- affected scope;
- current state;
- action taken;
- resolution state.

## 8. Override

Если override не описан — считай, что его нет.

Если есть:

- отдельное разрешение;
- reason required;
- confirmation;
- scope of override;
- duration, если применимо;
- audit event;
- визуальное предупреждение;
- возможность последующего review.

Не называй override обычным `Продолжить`.

## 9. Evidence

Для расследования важны:

- время;
- версия правила/policy, если хранится;
- входные данные/факты в допустимом объеме;
- решение;
- причина;
- последующее действие;
- actor;
- human approval/override.

UX должен помогать собрать историю без ручного сопоставления нескольких IDs.

## 10. Не показывать chain-of-thought

Объяснимость продукта означает:

- правило;
- факты;
- решение;
- причина;
- версия;
- доказуемая цепочка событий.

Она не требует показа внутреннего рассуждения LLM.

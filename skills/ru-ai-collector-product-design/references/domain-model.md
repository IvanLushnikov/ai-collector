# Доменная модель интерфейса AI-коллектора

Этот файл задает ментальную модель UX. Реальные API/схемы данных имеют приоритет.

## 1. Campaign

Кампания объединяет управляемый процесс пилотного взыскания.

Она может связывать:

- импортированную базу;
- настройки сценария;
- параметры запуска;
- compliance policy/ruleset;
- звонки;
- результаты;
- risk events;
- review items;
- audit events;
- отчет.

Не превращай кампанию в одну огромную форму. После создания она становится рабочим объектом с собственным состоянием и историей.

## 2. Debtor record

Запись должника — бизнес-запись, пришедшая из данных клиента.

Она не равна телефонному номеру и не равна звонку.

В зависимости от backend она может представлять человека, договор, обязательство или комбинацию этих сущностей. Не переименовывай ее без проверки схемы продукта.

В интерфейсе важно отделять:

- качество исходных данных;
- готовность записи к обработке;
- compliance eligibility для конкретного действия;
- историю попыток;
- бизнес-результат.

## 3. Compliance decision

Decision — моментальное решение о конкретном действии.

Минимальная UX-модель:

- decision id;
- action;
- subject/object;
- timestamp;
- result;
- reason(s);
- applied checks/rules;
- version/policy, если backend хранит;
- actor/system;
- связанное последующее событие.

Не трактуй прошлое `Allowed` как разрешение на будущий звонок: перед новым действием условия могли измениться.

## 4. Call attempt

Каждая попытка звонка — отдельная сущность.

Важные группы данных:

- когда инициирована;
- compliance decision;
- provider/line;
- технический статус;
- начало/конец;
- длительность;
- ошибки;
- conversation/result;
- usage events;
- audit links.

## 5. Conversation

Разговор существует только если модель продукта выделяет его отдельно.

Он может содержать:

- запись;
- транскрипт;
- события диалога;
- извлеченные факты;
- intent/outcome;
- QA result;
- handoff.

Не показывай LLM reasoning/chain-of-thought как пользовательское объяснение.

## 6. Business outcome

Outcome отвечает на вопрос «какой бизнес-результат получен?», а не «соединился ли звонок?».

Набор значений является бизнес-справочником и должен идти из продукта.

Всегда различай источник:

- определено системой;
- подтверждено человеком;
- изменено человеком;

только если backend это хранит.

## 7. Review item / handoff

Объект review должен быть адресным: пользователь понимает, что именно нужно решить.

Может ссылаться на:

- кампанию;
- должника;
- звонок;
- compliance decision;
- conversation;
- risk event.

Review item не должен существовать как абстрактная карточка без контекста.

## 8. Audit event

Audit event отвечает на вопрос «кто/что сделал и что изменилось?».

Типовые свойства:

- timestamp;
- actor;
- action;
- target;
- before/after, если уместно;
- reason;
- request/source;
- result.

Не делай frontend единственным источником audit events.

## 9. Usage event

Usage events могут быть намного более техническими и частыми.

Не выводи их в основную историю пользователя без агрегирования. Они полезны для:

- биллинга;
- диагностики;
- технического анализа;
- расчета потребления.

## 10. Связи, которые UX должен сохранять

Пользователь должен иметь возможность пройти цепочку:

`Campaign → Debtor record → Compliance decision → Call attempt → Conversation → Business outcome → Audit trail`

И обратную цепочку расследования:

`Risk event → affected call/action → decision → applied checks → campaign/debtor → human action`.

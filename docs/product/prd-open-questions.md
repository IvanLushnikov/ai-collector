## 1. Compliance и legal

Карта «закон → контроль → этап» собрана в [анализе технологического контура](../architecture/2026-08-17-technology-map.md). Продуктовый каталог правил: [rulebook v1](../compliance/rulebook-v1.md). Это не закрывает legal sign-off.

- Какие именно требования законодательства РФ фиксируем в v1 как обязательные системные правила, а не как общую формулировку?
- Какие сценарии должны считаться недопустимыми и блокироваться на уровне engine без возможности запуска?
- Какие параметры клиент может настраивать сам, а какие должны оставаться системно закрепленными?
- Нужны ли разные rulebook-профили для разных типов клиентов?
- Как юристы закрывают коллизию ст. 44.1‑1 закона о связи (согласие на автоматические вызовы) и ФЗ‑230 для портфеля пилотного клиента?

## 2. Stop conditions и автопауза

- Какой точный перечень событий автоматически переводит кампанию в защитное состояние?
- Что именно считаем исчерпанием допустимых попыток контакта?
- Должна ли автопауза включаться при падении качества распознавания или низкой уверенности модели?
- Кто и при каких условиях может возобновить кампанию после защитной остановки?

## 3. Метрики и экономика пилота

- Как именно измеряем снижение затрат: по операторскому времени, по стоимости контакта или по полной unit economics модели?
- С чем сравниваем результат пилота: текущий ручной процесс, аутсорс, существующий автодозвон или другой baseline?
- Какие численные значения считаем достаточными для успешного пилота?
- Как считаем снижение нагрузки на операторов: в звонках, часах, FTE или очереди handoff?

## 4. Качество voice/AI

- Чем подтверждаем целевой уровень качества распознавания на реальных данных?
- Какой порог низкой уверенности запускает fallback to human?
- Какие сценарии handoff обязательны, кроме общей спорной ситуации?
- Нужен ли жесткий state machine для первого релиза или допускается более свободный сценарий разговора?

## 5. Продуктовый scope v1

- Какие встроенные сценарии даем в v1 кроме базового подтверждения оплаты?
- Нужен ли в v1 отдельный интерфейс ручного добавления контактов или достаточно импорта файла на старте?
- Какая именно базовая статистика обязательна в первом релизе, а какая уже относится ко второму этапу?
- Нужно ли пользователю видеть только транскрипт или еще и структурированный итог звонка по фиксированным полям?

## 6. UX-разрывы пути `создание кампании → импорт → readiness → launch → calls → review → report` (по T-065)

- `создание кампании`: мастер реализован, но API-first ошибки и их inline-объяснение в UI пока не везде обязательны для перехода по шагам.
- `импорт`: в документации и API импорта есть качественный контракт, а в прототипе нужны единые статусы `accepted/rejected/errors` и привязка к конкретной сущности загрузки для принятия решения.
- `readiness`: для MVP нужны единые причины (`reasonCode + reasonText + nextAction`) по каждому этапу, иначе пользователь не понимает, из-за чего блокируется launch.
- `launch`: запуск/останов/возобновление должны быть привязаны к status transition API с обязательным подтверждением роли и audit trail.
- `calls`: карточка и список calls уже есть, но требуется консистентное доказательное представление для всех источников (`live` и `demo`) с цепочкой `compliance decisions + outcome + usage + qaStatus`.
- `review`: требуется единый список review-items с типом (`compliance`, `qa`, `risk`), приоритетом и обязательным следом решения (`approved/rejected/escalate/requeue`).
- `report`: сейчас доступны KPI, но без обязательного drill-down до первичного события сложно проводить операционный и legal review.

### Что считать приоритетом для MVP Lab

- Блокирующие: `launch` без auditable flow, отсутствие внятных API-first ошибок на импорте/readiness, отсутствие единых proof reasons до реального запуска.
- Условно-переходный: review-сборка и drill-down из report — минимальный уровень нужен уже на MVP для прозрачности операторов и QA.

## 7. IA и навигация MVP-кабинета

- Для `collection_manager` точка входа: `Кампании` → карточка кампании → `Обзор/База/Запуск/Звонки/Отчёт/Настройки`.
- Для `qa_analyst` точка входа: `Очередь проверок` → карточка review-item → детальный переход в `Кампания → Звонок`.
- Для `compliance_officer` точка входа: `Очередь проверок` и `Журнал действий`; внутри кампании — только нужные audit-ссылки и доказательства.
- Для `integration_admin` точка входа: `Интеграции` (источники, телефония, речь и модель), затем данные для подключения и диагностика. Свой ключ SpeechKit/YandexGPT/GigaChat — [ADR 0005](../decisions/0005-byok-speech-llm.md).

- Кампанийные сущности и действия в глобальный контур не выносим: `База`, `Сценарий`, `Телефония/проводка`, `Запуск`, `Звонки`, `Отчёт`, `Настройки`.
- В глобальном топ-левеле только сквозные объекты: `Кампании`, `Интеграции`, `Сценарии`, `Очередь проверок`, `Журнал действий`.
- Внутри кампании отчёты остаются контекстными, но ключевые risk/комплаенс сигналы дублируются в единственном глобальном экране `Очередь проверок`.

## 8. Операционная модель

- Кто на нашей стороне отвечает за разбор спорных звонков, настройку сценариев и корректировку правил во время пилота?
- Нужен ли ежедневный ручной review части звонков?
- Как будет устроен процесс обновления сценария без риска поломать running-кампанию?
- Где проходит граница между self-service и managed service в первом релизе?

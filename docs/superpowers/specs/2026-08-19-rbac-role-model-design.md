# Ролевая модель и матрица доступа для AI collector

Дата: 19.08.2026  
Статус: черновик для ревью в чате; после согласования можно детализировать до implementation plan  
Поверхность: backend auth/RBAC, клиентский кабинет, внутренний admin-контур, audit trail, evidence-доступ.

Главный принцип продукта не меняется: автоматизировать только то, что система может безопасно выполнить, объяснить и доказать. Ролевая модель не должна давать обход обязательных ограничений, tenant isolation или audit trail.

## 1. Зачем

Сейчас в проекте уже есть multi-tenant контур, audit log, разделение клиентского кабинета и внутренней поверхности, а также зачатки `RBAC v0`. Но права ещё не зафиксированы как единый контракт продукта и платформы. Из-за этого разные части системы рискуют по-разному трактовать один и тот же доступ: кто может запускать кампанию, кто видит запись разговора, кто может возобновить кампанию после системной остановки, кто имеет право на override и кто управляет пользователями tenant.

Нужно зафиксировать единую ролевую модель:

- для клиентской организации;
- для внутреннего/platform-контура;
- для high-risk операций;
- для чувствительных данных и evidence;
- для backend и UI как общего источника истины.

## 2. Scope и ограничения

Входит:

- роли и зоны ответственности;
- матрица `роль × действие × сущность`;
- различение клиентского и внутреннего контуров;
- правила для high-risk действий;
- требования к audit для операций доступа;
- границы первой версии RBAC.

Не входит:

- детальный UX всех экранов управления пользователями;
- SSO/OIDC/SAML;
- policy DSL;
- построчный ACL на каждую запись, если для этого нет реального сценария;
- финальный legal sign-off по тому, кто именно может делать `resume` после `auto_paused`.

Инварианты:

1. `platform role` не даёт автоматический доступ к данным tenant без явного policy path.
2. Любая операция высокого риска требует не только роль, но и проверку состояния объекта.
3. `override` не является обычным правом “писать”; это отдельный тип действия с усиленным аудитом.
4. Права на кампанию не равны правам на transcript/recording/evidence.
5. Tenant isolation обязателен для API, БД, логов и exports.

## 3. Архитектурный подход

Рекомендуемый подход для v1: **простая tenant-scoped RBAC**.

Это означает:

- базовый доступ выдаётся через роль;
- роль действует либо в рамках `tenant`, либо в рамках `platform`;
- UI может скрывать недоступные действия, но backend остаётся источником истины;
- критичные действия ограничиваются простой проверкой роли;
- итоговое решение логируется как audit event.

Почему так:

- для B2B SaaS v1 важнее быстро зафиксировать понятные роли, чем строить тонкую enterprise-схему;
- на старте достаточно закрыть доступ к данным, управлению пользователями и критичным действиям;
- детализацию по отдельным сущностям и policy gates лучше отложить до реальной необходимости.

## 4. Ментальная модель по аналогии с Linux

Используем Linux-аналогию как способ договориться о принципах, а не как буквальную схему прав:

| Linux | AI collector |
|---|---|
| `user` | `User` |
| `group` | назначение роли |
| `file/process/device` | доменный ресурс |
| `rwx` | доменные действия |
| `root` | ограниченные platform-роли |
| `sudo` | controlled override |
| `owner/group/others` | actor / same-tenant / platform actor |
| `auditd` | `AuditLog` + decision trail |

Аналог `sudo` в продукте нужен, но только в управляемом виде:

- с явной причиной;
- с actor/role;
- с before/after state;
- с привязкой к объекту и evidence;
- с отдельным отображением в аудите.

## 5. Акторы и scope

### 5.1. Типы actor

- `tenant_user` — сотрудник клиентской организации;
- `platform_user` — сотрудник нашей компании;
- позже: `service_account` для системных интеграций и jobs.

### 5.2. Scope

- `platform` — внутренняя поверхность и платформенные операции;
- `tenant` — данные и операции одной организации.

Для v1 этого достаточно: пользователь либо работает внутри своей организации, либо во внутреннем/platform-контуре. Более мелкий scope можно добавить позже, если он реально понадобится.

## 6. Роли v1

### 6.1. Клиентский контур

| Роль в продукте | Код роли | Назначение |
|---|---|---|
| Владелец организации | `tenant_owner` | полный доступ внутри своей организации, включая пользователей и критичные действия |
| Менеджер кампаний | `campaign_manager` | создание и ведение кампаний, работа со звонками, отчётами и настройками кампании |
| Наблюдатель | `tenant_viewer` | только просмотр кампаний, звонков, отчётов и журнала действий |

### 6.2. Внутренний/platform-контур

| Роль в продукте | Код роли | Назначение |
|---|---|---|
| Администратор платформы | `platform_admin` | управление платформой, но не автоматический доступ ко всем данным клиентов |
| Оператор поддержки | `support_engineer` | диагностика проблем клиента через отдельный support path |

Принцип: внутренние роли отделены от клиентских. `platform_admin` не должен автоматически становиться `tenant_owner`, а `support_engineer` не должен видеть клиентские данные без явного основания.

## 7. Зоны доступа v1

Чтобы не усложнять RBAC на старте, права группируются не по десяткам сущностей, а по пяти рабочим зонам:

- `Кампании`
- `Звонки`
- `Отчёты`
- `Интеграции`
- `Пользователи`

Отдельно сохраняется служебная зона:

- `Журнал действий`

Если позже понадобится более тонкое разделение, эти зоны можно будет развернуть в отдельные ресурсы backend-модели.

## 8. Действия v1

Для v1 достаточно короткого набора действий:

- `просмотр`
- `создание`
- `изменение`
- `запуск`
- `пауза/остановка`
- `управление пользователями`
- `управление интеграциями`
- `экспорт`

Классы риска:

| Класс | Действия |
|---|---|
| низкий | просмотр |
| средний | создание, изменение |
| высокий | запуск, пауза/остановка, управление пользователями, управление интеграциями, экспорт |

## 9. Матрица доступа v1

Обозначения:

- `Y` — разрешено;
- `R` — только просмотр;
- `N` — запрещено.

### 9.1. Клиентские роли

| Роль в продукте | Код роли | Кампании | Звонки | Отчёты | Интеграции | Пользователи | Журнал действий |
|---|---|---|---|---|---|---|---|
| Владелец организации | `tenant_owner` | `Y` | `Y` | `Y` | `Y` | `Y` | `R` |
| Менеджер кампаний | `campaign_manager` | `Y` | `Y` | `Y` | `R` или `Y` в пределах настройки кампании | `N` | `R` |
| Наблюдатель | `tenant_viewer` | `R` | `R` | `R` | `N` | `N` | `R` |

### 9.2. Внутренние роли

| Роль в продукте | Код роли | Платформа | Данные клиента |
|---|---|---|---|
| Администратор платформы | `platform_admin` | `Y` | `N` по умолчанию |
| Оператор поддержки | `support_engineer` | `R` | `N` по умолчанию; доступ только через отдельный support path |

Эта матрица умышленно консервативна: если право спорно, default — `N`.

## 10. Два специальных правила поверх ролей

### 10.1. Критичные действия клиента

Следующие действия лучше не раздавать широко:

- управление пользователями;
- критичное управление интеграциями;
- экспорт чувствительных данных;
- запуск и остановка кампании, если команда хочет держать это у owner.

Минимальное правило v1:

1. `tenant_owner` может всё внутри tenant;
2. `campaign_manager` не управляет пользователями;
3. `tenant_viewer` ничего не меняет.

### 10.2. Внутренний доступ к данным клиента

Внутренние роли не получают постоянный доступ к данным клиента.

Минимальное правило v1:

1. `platform_admin` управляет платформой, но не читает клиентские данные по умолчанию;
2. `support_engineer` получает доступ только по отдельному support path;
3. такой доступ должен быть явно зафиксирован в аудите.

## 11. Audit и доказуемость

Для high-risk операций обязательно писать:

- `actorUserId`
- `actorRole`
- `tenantId`
- `resourceType`
- `resourceId`
- `action`
- `decision` (`allowed` / `denied`)
- `comment`
- `correlationId`
- `createdAt`

Минимум следующие действия всегда аудитируются:

- `manage_members`
- `launch`
- `pause`
- `stop`
- `manage_credentials`
- `export`

## 12. Техническая реализация v1

### 12.1. Модель данных

Минимум:

- `User`
- `Tenant`
- `TenantMembership` (`userId`, `tenantId`, `roleName`)
- `PlatformMembership` или эквивалент для внутренних ролей

Опционально позже:

- `RolePermission`
- `SupportAccessGrant`

### 12.2. Авторизационный слой

Нужен единый authorizer:

```ts
authorize(actor, action, resource, context)
```

Он проверяет:

1. identity;
2. tenant или platform scope;
3. role capability;
4. необходимость audit trail.

### 12.3. Где проверять

Проверки обязательны в двух местах:

- на уровне route;
- на уровне доменного transition.

Это нужно, чтобы UI или внешний клиент не могли обойти ограничения прямым вызовом API.

## 13. Порядок внедрения

Рекомендуемая последовательность:

1. Зафиксировать enum ролей и список capabilities.
2. Ввести authorizer как единый слой.
3. Защитить критичные действия: `launch`, `stop`, `manage_members`, `manage_credentials`, `export`.
4. Подключить аудит решений доступа.
5. Только после этого дорисовывать UI управления пользователями и role-based visibility экранов.

## 14. Открытые вопросы

1. Может ли `campaign_manager` сам запускать кампанию, или запуск остаётся только у `tenant_owner`?
2. Даём ли `campaign_manager` право менять интеграции организации, или только настройки внутри кампании?
3. Нужен ли `tenant_viewer` уже в v1, или достаточно owner + manager?
4. Какой именно support path допустим для `support_engineer`?

## 15. Что сознательно оставляем на потом

В enterprise-этап выносятся:

- отдельные роли `compliance_officer`, `qa_analyst`, `auditor_readonly`;
- тонкая матрица по transcript/recording/evidence;
- per-resource policy gates;
- break-glass / dual approval;
- platform security roles шире двух базовых;
- точечные ограничения уровня `campaign`/`recording`/`review_item`.

## 16. Критерии готовности этой модели

Модель считается достаточно определённой для перехода к implementation plan, если:

1. Для каждой ключевой роли понятны её рабочие решения в продукте.
2. Для `launch`, `manage_members`, `manage_credentials` и `export` есть однозначный owner.
3. Клиентские и внутренние роли не смешиваются.
4. Матрица доступа может быть напрямую отражена в backend authorizer.
5. UI может опираться на неё для скрытия/показа действий, не становясь источником истины.

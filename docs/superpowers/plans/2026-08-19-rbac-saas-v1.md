# RBAC SaaS v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Внедрить простую tenant-scoped ролевую модель B2B SaaS v1 без enterprise-усложнений: клиентские роли `tenant_owner`, `campaign_manager`, `tenant_viewer`; внутренние роли `platform_admin`, `support_engineer`.

**Architecture:** Сохранить текущий backend как источник истины для прав доступа, но заменить разрозненные endpoint-level списки ролей на единый authorizer по зонам доступа. На первом этапе сохраняется header-based режим (`X-User-Role`), затем добавляется разрешение роли из membership-моделей и минимальный support path.

**Tech Stack:** Node 20, TypeScript, Fastify, Prisma, PostgreSQL 16, Vitest.

**Spec:** `docs/superpowers/specs/2026-08-19-rbac-role-model-design.md`

## Global Constraints

- Использовать простую tenant-scoped RBAC.
- Клиентские и внутренние роли не смешивать.
- `platform_admin` не получает автоматический доступ к данным клиента.
- `support_engineer` получает доступ только через отдельный support path с аудитом.
- `tenant_owner` управляет пользователями и критичными действиями.
- `campaign_manager` не управляет пользователями.
- `tenant_viewer` ничего не меняет.
- Backend остаётся источником истины; UI только скрывает недоступные действия.
- Всегда сохранять tenant isolation и audit trail для критичных действий.

## File Structure

- `docs/security/rbac.md` — каноническое описание ролей, зон доступа и endpoint-level правил.
- `src/domain/authz/*` или `src/server/authz/*` — единый authorizer и role normalization.
- `src/server/middleware/role*` — чтение и нормализация роли из header/auth context.
- `src/routes/campaigns.ts`, `src/routes/calls.ts`, `src/routes/reports.ts`, `src/routes/usage.ts`, `src/routes/compliance.ts` — применение authorizer на существующие endpoints.
- `src/routes/provider-credentials.ts`, `src/routes/telephony*.ts` — ограничения на интеграции и credentials.
- `src/db/prisma/schema.prisma` и `src/domain/*membership*` — membership-модели, если текущая схема ещё не покрывает SaaS v1.
- `src/routes/tenant-users.ts` — минимальный API управления пользователями tenant.
- `tests/*` — regression-покрытие по новым ролям и отказам.

## Task Outline

### Task 1: Зафиксировать SaaS v1 роли и legacy-совместимость
- [ ] Синхронизировать `docs/security/rbac.md` со спекой.
- [ ] Зафиксировать canonical roles: `tenant_owner`, `campaign_manager`, `tenant_viewer`, `platform_admin`, `support_engineer`.
- [ ] Описать legacy alias mapping для старых значений `owner`, `collection_manager`, `operator`, `integration_admin`, `qa_analyst`, `compliance_officer`.

### Task 2: Ввести единый role normalization layer
- [ ] Добавить нормализацию роли из `X-User-Role` и будущего auth context.
- [ ] Отдавать единый canonical role в request context.
- [ ] Покрыть alias/unknown role тестами.

### Task 3: Ввести authorizer по зонам доступа
- [ ] Добавить authorizer для зон `campaigns`, `calls`, `reports`, `integrations`, `users`, `audit_logs`.
- [ ] Описать простую матрицу доступа на уровне кода.
- [ ] Сохранить route-level и domain-level проверку.

### Task 4: Перевести существующие campaign/calls/report/audit endpoints на authorizer
- [ ] Заменить разрозненные списки ролей на вызовы authorizer.
- [ ] Сократить доступы до SaaS v1 ролей и alias-совместимости.
- [ ] Обновить тесты и документацию endpoint-ов.

### Task 5: Упростить доступ к интеграциям и credentials
- [ ] Определить, что в SaaS v1 разрешено `tenant_owner`, а что `campaign_manager`.
- [ ] Ограничить telephony/provider credentials endpoints по новой модели.
- [ ] Зафиксировать audit для критичных действий с интеграциями.

### Task 6: Перевести роль с mock-header на membership resolution
- [ ] Разрешать каноническую роль из membership-связи пользователя и tenant.
- [ ] Сохранить header-based режим как dev fallback, пока real auth не завершён.
- [ ] Проверить tenant isolation и отсутствие смешения `platform` и `tenant` ролей.

### Task 7: Добавить минимальный tenant user management
- [ ] Создать минимальный API списка пользователей tenant и смены роли.
- [ ] Разрешить управление только `tenant_owner`.
- [ ] Писать audit события на изменение роли и состав tenant.

### Task 8: Добавить support access path
- [ ] Зафиксировать минимальный `SupportAccessGrant` contract.
- [ ] Дать `support_engineer` только временный и аудитируемый путь в tenant.
- [ ] Не открывать постоянный доступ к данным клиента по platform-роли.
